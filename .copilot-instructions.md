### Crawler Agent - Full Crawl Execution

**Location:** `agents/crawler/main.py` (port 8015)

**⚠️ Critical API Format:** The crawler endpoint expects `ToolCall` format with `args` (list) and `kwargs` (dict). HTTP 422 errors indicate incorrect JSON format.

**Launch full crawl (correct format):**
```bash
# CORRECT: ToolCall format with args and kwargs
curl -X POST http://localhost:8015/unified_production_crawl \
  -H "Content-Type: application/json" \
  -d '{
    "args": [["domain1.com", "domain2.com", ...]],
    "kwargs": {
      "max_articles_per_site": 5,
      "concurrent_sites": 3
    }
  }' \
  --max-time 120

# Response on success (HTTP 202 Accepted):
# { "job_id": "abc123...", "status": "accepted" }
```

**Important timeout requirements:**
- Use `--max-time 120` (2 minutes minimum) for crawl submissions
- Crawler may take time validating domains and initializing before responding
- Short timeouts (15-30 sec) will cause spurious read timeout errors

**Query available jobs:**
```bash
curl http://localhost:8015/jobs
# Returns: { "job_id1": "PENDING", "job_id2": "COMPLETED", ... }
```

**Check individual job status:**
```bash
curl http://localhost:8015/job_status/{job_id}
# Returns full job details including status, timestamps, results
```

**Stop a running job:**
```bash
curl -X POST http://localhost:8015/stop_job/{job_id}
```

## Common Startup Issues & Troubleshooting

### Issue: ModuleNotFoundError: No module named 'agents'
**Cause:** PYTHONPATH not set when running agents via `conda run`  
**Solution:** Always include PYTHONPATH in conda run command:
```bash
conda run -n justnews-py312-phase1 bash -c 'export PYTHONPATH=/home/adra/justnewsA0:$PYTHONPATH && python -m agents.crawler.main'
```

### Issue: Crawl job stuck in "pending" state (CRITICAL)
**Symptom:** Job remains in "pending" status indefinitely with frozen `updated_at` timestamp  
**Root Cause:** Crawler process exists in `ps aux` but Uvicorn FastAPI server failed to start or crashed. Asyncio background tasks only execute if the event loop is running - if the process exits, queued jobs never transition from "pending" to "running".  
**Diagnosis:**
```bash
# 1. Check if crawler process exists (will show PID)
ps aux | grep "agents.crawler.main" | grep -v grep

# 2. Check if port 8015 is actually listening (THIS IS CRITICAL)
ss -tlnp | grep 8015
# If port 8015 doesn't appear, the FastAPI server is NOT running

# 3. If process exists but port doesn't listen, the process is dead/crashed
curl http://localhost:8015/health  # Will fail if port not listening
```
**Solution:** **Restart the crawler cleanly:**
```bash
# 1. Kill existing crawler process
pkill -f "agents.crawler.main"
sleep 2

# 2. Restart crawler with proper PYTHONPATH
conda run -n justnews-py312-phase1 bash -c 'export PYTHONPATH=/home/adra/justnewsA0:$PYTHONPATH && python -m agents.crawler.main' &

# 3. Wait and verify it's healthy (BOTH process AND port must be present)
sleep 3
curl http://localhost:8015/health  # Should return: {"status": "ok"}

# 4. Resubmit the crawl job (old one is lost, but data is safe)
```
**Prevention:** Always verify both process existence AND port listening when checking service health:
```bash
# INCOMPLETE CHECK (false positive - process exists but server crashed):
ps aux | grep crawler  # ❌ Not enough!

# COMPLETE CHECK (verifies server actually listening):
curl -s http://localhost:8015/health | jq .status  # ✓ Correct!
```
**Learning:** Process existence doesn't guarantee service readiness. Always verify the listening port and perform API health checks.

### Issue: Crawler fails with "Failed to connect to MCP Bus"
**Cause:** MCP Bus not started before Crawler, or MCP Bus startup incomplete  
**Solution:** Start services in order (MCP Bus first):
```bash
# 1. Start MCP Bus (REQUIRES_BUS=0 since it has no dependencies)
REQUIRE_BUS=0 /usr/local/bin/justnews-start-agent.sh mcp_bus
sleep 5  # Wait for MCP Bus to fully initialize

# 2. Then start Crawler (will wait for MCP Bus to be ready)
/usr/local/bin/justnews-start-agent.sh crawler
```

### Issue: HTTP 422 when submitting crawl job
**Cause:** Incorrect JSON payload format (using direct fields instead of ToolCall format)  
**Solution:** Use correct format with `args` and `kwargs`:
```bash
# WRONG (will return 422):
{"domains": [...]}

# CORRECT:
{"args": [[...]], "kwargs": {...}}
```

### Issue: HTTP timeout when submitting crawl
**Cause:** Timeout too short (default curl is 30 sec, crawl initialization takes longer)  
**Solution:** Use longer timeout:
```bash
curl --max-time 120 -X POST http://localhost:8015/unified_production_crawl ...
```

### Issue: Job submitted successfully (HTTP 202) but never progresses
**Symptom:** Crawler returns valid job_id, but job stays in "pending" state indefinitely  
**This is the "stalled job" issue** - see "Crawl job stuck in 'pending' state" section above  
**Quick diagnostics:**
```bash
# 1. Verify crawler port is actually listening
ss -tlnp | grep 8015 || echo "PORT NOT LISTENING - Crawler process crashed!"

# 2. Check job in database
curl http://localhost:8015/job_status/$JOB_ID | jq '.updated_at'
# If updated_at equals created_at (hasn't changed), job never processed
```

### Issue: Crawler process consumes excessive memory
**Status:** NORMAL - Not an issue  
**Explanation:** Crawler memory usage grows during active crawl:
- Idle: ~300-500 MB
- During crawl: 1-3 GB (normal for concurrent web scraping + LLM analysis)
- Monitor with: `ps aux | grep 'agents.crawler' | grep -v grep`
- Memory plateauing or not shrinking after crawl completes may indicate resource leak

### Issue: Process shows running but API not responding
**Cause:** Process exists but Uvicorn/FastAPI server never bound to port (common during startup)  
**Solution:** Wait for full initialization:
```bash
# Wait up to 10 seconds for server startup
for i in {1..10}; do
  curl -s http://localhost:8015/health && echo " ✓ Ready" && break
  sleep 1
  echo "[$i] Waiting for crawler to become ready..."
done
```
**If still not responding after 10 seconds:** Check process is truly running:
```bash
ps aux | grep "agents.crawler.main" | grep -v grep
# If no output, process exited - check permissions, PYTHONPATH, conda env
```

### Issue: Job submitted but no response (appears hung)
**Cause:** Crawler is processing - check with `/jobs` endpoint
**Solution:** Query job status without re-submitting:
```bash
curl http://localhost:8015/jobs  # See all jobs and their status
```

## Common Mistakes to AVOID

❌ **DON'T:**
- Rebuild environments without explicit instruction (they exist and work)
- Modify global.env without understanding the cascading effects
- Assume one environment can handle all phases (they're intentionally isolated)
- Run GPU code in CPU-only environments (Phase 2/4)
- Skip health checks after system restarts
- Modify systemd service files without reloading with `sudo systemctl daemon-reload`
- Force stop vLLM during model load (wait for /health endpoint)
- Ignore CUDA device allocation (CUDA_VISIBLE_DEVICES controls visibility)
- Start Crawler before MCP Bus is ready (dependencies matter!)
- Forget to set PYTHONPATH in conda run commands (modules won't import)
- Use short timeouts for long-running operations like crawl submissions
- Submit crawl with incorrect JSON format (must use ToolCall format with args/kwargs)
- Assume service is ready just because port is listening (verify with actual API call)
- Assume process is healthy just because it appears in `ps aux` (verify port is listening!)
- Ignore a stalled job for >5 minutes - restart crawler and resubmit
- Assume process crash automatically recovers - always manually restart after crashes

✅ **DO:**
- Always check current state first (conda env list, systemctl status, curl /health)
- Document your understanding of the problem before solving
- Run validation checks after changes (`make lint`, `get_errors`, health checks)
- Use phased test scripts to verify changes in isolation
- Preserve environment isolation - changes in one phase shouldn't affect others
- Check logs after any failure (journalctl, agent logs, error output)
- Follow the canonical startup sequence for fresh system starts
- Set PYTHONPATH explicitly in all `conda run` agent commands
- Start MCP Bus before any dependent agents (Crawler, Synthesizer, etc.)
- Use `--max-time 120` or longer for HTTP requests to long-running operations
- Use ToolCall format (args + kwargs) for crawler API submissions
- Wait 5-10 seconds between starting MCP Bus and dependent services
- Query `/jobs` endpoint to check crawl status without re-submitting
- Monitor crawler memory usage - 1-3 GB during active crawl is normal
- Always verify BOTH process existence AND port listening when checking service health
- Use `ss -tlnp | grep PORT` to verify port is actually listening before trusting service
- If a job is stuck in "pending" for >5 minutes, assume process crashed and restart crawlers
- After crawl job succeeds, mark it as a known-good baseline for future diagnostics

## Diagnostic Procedures

### Diagnosing a Stalled Crawl Job (Step-by-Step)

If a crawl job is submitted (HTTP 202 accepted) but never progresses:

**Step 1: Check if crawler port is listening (CRITICAL)**
```bash
ss -tlnp | grep 8015
# RESULT 1: Shows listening on 8015 → Server is running, job may just be slow
# RESULT 2: No output → Server crashed! Port not listening!
```

**Step 2: Verify if job is actually running or stuck**
```bash
curl -s http://localhost:8015/job_status/$JOB_ID | jq '{status, created_at, updated_at}'

# NORMAL (job progressing):
# {
#   "status": "completed",
#   "created_at": "2026-02-03T14:34:25",
#   "updated_at": "2026-02-03T14:34:31"  ← updated_at is NEWER than created_at
# }

# STALLED (job stuck in pending):
# {
#   "status": "pending",
#   "created_at": "2026-02-03T13:58:19",
#   "updated_at": "2026-02-03T13:58:19"  ← SAME TIME - never updated!
# }
```

**Step 3: If job is stalled AND port not listening, restart crawler**
```bash
# Kill any existing processes
pkill -f "agents.crawler.main"
sleep 2

# Verify port is now free
ss -tlnp | grep 8015 || echo "Port freed"

# Restart with proper PYTHONPATH
conda run -n justnews-py312-phase1 bash -c 'export PYTHONPATH=/home/adra/justnewsA0:$PYTHONPATH && python -m agents.crawler.main' &

# Wait and verify startup
sleep 5
curl -s http://localhost:8015/health | jq .  # Should show {"status": "ok"}
```

**Step 4: Resubmit crawl job**
```bash
# Old job is abandoned (but safe in database)
# Submit new job with same parameters
curl -X POST http://localhost:8015/unified_production_crawl \
  -H "Content-Type: application/json" \
  -d '{"args": [[domains...]], "kwargs": {...}}' \
  --max-time 120

# New job should transition from pending to completed
```

## Service Startup Order & Dependencies

**Critical dependency chain for full system startup:**

```
1. MCP Bus (port 8000)          ← START FIRST (no dependencies)
   └─ Wait 5-10 seconds for initialization

2. Crawler Agent (port 8015)    ← Depends on MCP Bus
3. Synthesizer Agent (port 8010) ← Depends on MCP Bus
4. Other Agents                 ← All depend on MCP Bus
```

If you start Crawler before MCP Bus is ready, it will fail with "Failed to connect to MCP Bus" even if MCP Bus is now running. Always restart dependent agents after ensuring MCP Bus is healthy.

## When to Ask for Help

Contact a system administrator if:
- A phased environment needs rebuilding (don't attempt without guidance)
- vLLM fails to load the model (GPU memory or CUDA issues)
- Database connectivity fails (MariaDB/ChromaDB connection problems)
- Systemd services won't start (permission or path issues)
- You need to modify `/etc/justnews/global.env` (requires sudo)
- Unsure about environment isolation impacts
- MCP Bus fails to initialize despite correct startup command
- Persistent 422 errors from crawler endpoint (check JSON format first)
- Need to diagnose why a crawl job failed (check error_message field first)

**Before escalating, always try:**
1. Verify port is listening: `ss -tlnp | grep 8015` (for crawler)
2. Check with API directly: `curl http://localhost:8015/health`
3. Restart cleanly: kill process, wait 2 sec, restart with proper PYTHONPATH
4. Resubmit job if stuck in pending after restart
5. Check crawler logs: `sudo journalctl -u justnews@crawler -n 100`
